# CodeAgent 待做计划：实现 Session 存储与会话管理

## 一、目标与范围

本计划已确认并落盘，用于指导后续实现模型分任务完成 Session。此次仅更新文档，不代表下面的功能已经实现或验证。

原工具计划已完整保存到 [基础工具实施记录.md](./基础工具实施记录.md)，其中既有工具、Agent 验收记录和报告链接继续保留，不重置历史结论。

本轮只实现 Session 包及必要依赖调整，让调用方能够：

- 创建、管理和归档会话。
- 保存 Run、消息、模型来源和工具执行记录。
- 按 Run 读取完整任务。
- 读取、选择历史分支。
- 查询中断任务并显式记录恢复结果。

**不修改 Agent、Runtime、LLM、Provider、工具、demo 或实际配置。** Agent 与 Session 的接入、停止任务、关闭实例、事件通知和工具执行前后的调用编排，留给后续 Runtime 阶段。

SQLite 是唯一持久化来源；JSON 只用于数据库字段，不维护第二份 JSONL。暂不实现压缩、Memory、自定义记录、永久删除、会话复制、导入导出或附件文件管理。

## 二、包结构与职责

采用以下包划分（2026-10-01 更新，以本节取代旧的同包要求）：

- `internal/session`：Service、Session、历史和工具记录的业务规则。
- `internal/session/config`：共享记录、状态、查询参数、错误和消息编解码；不读取 TOML。
- `internal/session/store`：数据库连接、事务、初始化迁移及表记录读写。
- `internal/session/sql`：集中定义 SQL，不执行语句，不依赖上层包。

Store 保持五个正式文件：`store.go`、`init.go`、`sessions.go`、`runs.go`、`entries.go`。Codec 在 config 包，不放在 Store。业务检查与写入仍使用同一 Store 事务；外层不能直接访问数据库或 SQL 事务私有字段。

保留三个具体对象，不增加通用存储后端接口：

| 对象 | 职责 |
|---|---|
| `Store` | 数据库连接、初始化、SQL 和事务 |
| `Service` | 多会话的创建、查询、列表、重命名、归档和打开 |
| `Session` | 绑定 SessionID，提供该会话的 Run、消息、工具执行和分支操作 |

文件按职责划分；方法不必与接收者结构体放在同一文件。不要让每条 SQL 都经过三层原样转发。

Session 不持有 Agent，不启动后台循环，不维护用户输入队列。不同会话可以并发调用存储方法；同会话只允许一个未结束 Run，通过存储事务保证。

### 类型调整

- 保留四类持久化记录：`SessionInfo`、`RunRecord`、`Entry`、`ToolExecution`。
- 保留每条 assistant Entry 的 `MessageModelOrigin`。
- 删除 `RunRecord.Usage` 的重复持久化字段。
- 保留 `ModelUsage` 作为查询汇总结果。
- 增加 `RunDetail`：包含 RunRecord、Entries、ToolExecutions、按来源用量和总用量。
- 增加小型 `RunCompletion`：包含 State、StopReason、RawStopReason、ErrorMessage，供结束 Run 使用。
- 已消费的纠正保存为普通 UserMessage；不增加消息种类。
- 不增加未使用的扩展结构体、通用属性 map 或深拷贝体系。

## 三、功能与行为约定

### 数据库打开、初始化和版本

- `Open(ctx, path)` 打开数据库并检查连接，返回 Store。
- `Store.Init(ctx)` 显式检查版本、创建或升级表结构。
- `Store.Close()` 关闭数据库连接。
- Init 成功后才创建 Service；初始化不标记任何 Run 中断。

沿用 `modernc.org/sqlite` 和驱动名 `sqlite`，删除手工注册 `sqlite3` 的兼容逻辑。path 按文件路径处理，正确处理中文、空格及 URI 特殊字符，不兼容任意驱动 DSN。

每个连接启用外键及 5 秒 busy timeout。首版每个 Store 最多一个打开连接并保留一个空闲连接；事务内所有操作使用事务对象，避免调用 Store 的普通查询造成等待自身连接。

使用 `PRAGMA user_version` 管理表结构和消息格式版本，初始化与版本写入在同一事务中完成：

- 新数据库建立四表。
- 兼容当前已知的无版本四表结构，保留已有数据。
- 新结构不再保存 Run 用量汇总；旧库中的 `usage_json` 可以保留但不再读写。
- 不认识的旧结构或更高版本明确报错，不删除数据库重建。

时间继续使用 UTC RFC3339Nano；按时间查询排序时，使用数据库时间函数并追加 ID 作为稳定排序条件，不直接依赖可变小数位字符串排序。

### 会话管理

Service 提供：

- 创建：传入标题、工作目录，生成 UUID 与时间，初始 HeadID 为空。
- 获取：按 SessionID 返回 SessionInfo。
- 列表：支持 limit、offset、active／archived／all 三态归档筛选和字面标题搜索；默认 active。
- 重命名：拒绝空白标题，更新标题与更新时间。
- 自动标题：SetTitleIfEmpty 仅填空标题；归档后同样拒绝修改。
- 目录绑定：允许未绑定的纯聊天会话；首次绑定检查目录，归档或存在未结束 Run 时拒绝。
- 归档、取消归档：更新 ArchivedAt 和更新时间。
- 打开：拒绝归档会话，返回绑定 SessionID 的轻量 Session；不加载模型配置、不启动 Agent。

列表默认 50 项，最大 200；拒绝负数。不存在记录时保留可由 `errors.Is(err, sql.ErrNoRows)` 判断的错误。

归档会话仍允许读取，拒绝开始新 Run。归档、切换分支时存在未结束 Run，则返回明确错误；Session 不负责取消它。重复归档或取消归档按幂等操作处理。

### Run 与消息

Session 提供下列操作：

| 操作 | 输入与结果 |
|---|---|
| 开始 Run | 调用方提供 RunID 和 UserMessage，返回 RunRecord |
| 记录一次调用尝试 | RunID，原子增加 Steps 并返回新值 |
| 追加消息 | RunID、Message、可选 Origin，返回 Entry |
| 结束 Run | RunID、RunCompletion，返回最终 RunRecord |
| 读取 Run | RunID，返回 RunDetail |
| 列出 Run | 分页参数，返回本会话各分支的 RunRecord |
| 读取当前历史 | 返回当前 Head 的完整祖先链 Entries |

RunID 由未来调用方生成，要求跨重启唯一；Session 和 Entry ID 使用现有 UUID 依赖生成。Run 的时间和 Sequence 由存储层设置，消息自身 Timestamp 保留原值。

开始 Run 在同一事务中：

```text
检查会话及未结束任务
→ 创建 Run
→ 写入用户 Entry
→ 设置 InputEntryID、LastEntryID
→ 更新 Session.HeadID 和更新时间
```

追加消息在同一事务中更新 Entry、Run.LastEntryID、Session.HeadID 和更新时间：

- ParentID 接当前 Head。
- Sequence 在整个会话内递增，切换分支不重置。
- 检查 Run、父记录和会话归属，禁止跨会话关联。
- 只能向当前未结束 Run 追加。
- assistant 消息必须提供实际请求 Origin；用户与工具结果不重复填写。
- 保留成功、失败、取消、截断及异常响应的原始内容。
- 不在存储层判断响应能否执行工具或进入下一次模型上下文。

结束 Run 只更新任务结果和结束时间，不追加虚构消息。State 必须为终态；停止原因遵循当前约定。已结束 Run 再次结束返回明确冲突，不覆盖原结果。

Run 列表按输入 Entry 的 Sequence 倒序排列。RunDetail 的 Entries 按 Sequence 正序排列，不混入其他 Run。

用量读取时从该 Run 的 assistant 消息按完整 Origin 汇总；不重复累计 ToolResultMessage 中的 Usage，也不把 Reasoning 再加进 Output 或 Total。费用沿用消息中的已有数值。

### 工具执行记录

保留 ToolExecution，区分执行过程与最终工具返回内容。

提供两个存储操作：

- **记录开始**：接收 AssistantEntryID 和 ToolCallID，推导所属 Run 与会话，生成 StartedAt。
- **追加工具结果**：接收 AssistantEntryID 和 ToolResultMessage；保存结果 Entry，如果存在开始记录，同时填写 FinishedAt 与 ResultEntryID。

规则：

- `(AssistantEntryID, ToolCallID)` 唯一定位调用；校验对应 assistant 中确实存在且唯一。
- 同一调用不得重复保存结果。
- 工具结果必须与对应调用配对，不能只按 ToolCallID 全局查找。
- 开始记录与工具结果的会话、Run 必须一致。
- 有开始记录时，结果 Entry 与执行结束更新在同一事务提交。
- 没有开始记录也可保存明确的“未执行”或“未知工具”结果，不伪造开始时间。
- 结果按实际提交顺序追加。Session 不等待整批工具，也不重新按调用顺序排列原始历史。
- 普通消息追加入口不接受工具结果，统一经过工具结果操作，避免绕过关联检查。

Session 不执行工具、不补造缺失结果、不自动重试。查询发现有开始无结果，只能表达“结果未知”。

### 分支与中断记录

选择分支的输入为 RunID：

- 必须属于当前会话且已经结束。
- 当前会话没有未结束 Run，才能切换。
- 将 HeadID 指向该 Run.LastEntryID，更新会话时间。
- 后续 Run 从这个位置开始，旧分支保留。
- 读取当前分支沿 ParentID 追溯后反转为正序；不能直接读取整个会话的所有消息当作上下文。
- 不实现任意 Entry 中间分叉或文件回滚。

Service 提供 ListUnfinishedRuns，以及将指定未结束 Run 标记为中断的 MarkRunAborted；判断与最终写入位于同一事务。Store 只提供查询与终态更新原语：

- State 设为 aborted，清空停止原因，记录“程序中断”和结束时间。
- 保留消息、工具开始记录及已有工具结果。
- 已结束 Run 不被恢复方法覆盖。
- Init、GetSession、OpenSession 不自动执行恢复。
- 未来 Runtime 确认对应任务不再运行后才调用；本轮只实现存储方法和本地验证。

### Codec 与错误

- 继续保存统一 LLM 消息 JSON，不引入逐字段复制的 wire 类型。
- config.EncodeMessage 使用标准 JSON 编码；config.DecodeMessage 负责统一消息恢复。
- 非空与 Role 一致性在消息追加入口集中检查一次。
- 解码保留角色分派、具体错误、`UseNumber` 和未知字段拒绝。
- JSON 数字恢复为 `json.Number`，不承诺恢复原来的 Go 数值类型。
- 时间、JSON 或来源解码失败时返回错误，不静默跳过。
- 图片继续以内联 base64 保存。
- 存储方法返回 error，不发 Agent 事件，不决定是否停止运行。
- 错误保留底层原因；关联错误、已结束 Run、归档冲突提供少量可判断的错误，不建立完整错误码框架。

  - 新库初始化直接生成 v2 结构并写入 `user_version = 2`；

  - 数据库 Close 后重新 Open 并 Init 通过。

### 任务四：工具执行存储与关联唯一性

状态：已实现；已按审计标准通过本地验收。

- 实现状态：已实现。
- 实际改动：
  - `Entry` 结构体增加 `AssistantEntryID` 与 `ToolCallID` 字段；`entries` 表建立 `(assistant_entry_id, tool_call_id)` 部分唯一索引。
  - `RecordToolStart` 与 `AppendToolResult` 均校验对应 assistant 消息内确实声明该 `ToolCallID` 且仅声明一次；若声明多次返回具体重复错误。
  - `RecordToolStart` 增加结果已存检查：若 `entries` 中已存在该调用结果，拒绝记录启动并返回 `ErrToolResultConflict`。
  - `AppendToolResult` 无论是走已有启动记录路径还是无启动记录路径（未执行/未知工具），均在单事务内检查 `entries` 查重，写入带关联字段的结果 Entry，若有启动记录同步更新 `tool_executions`；重复保存均被拒绝。
- 已运行场景及结果：
  - 有启动记录、无启动记录两条路径重复提交结果均被拦截并返回 `ErrToolResultConflict`；
  - 结果已保存后再次尝试 `RecordToolStart` 被拦截；
  - Assistant 内含有重复 `ToolCallID` 时，启动和保存结果均被拦截；
  - 两个 Assistant 使用相同 `ToolCallID` 时，各自正确关联其所属的 `AssistantEntryID`，互不干扰；
  - 并发提交相同工具结果严格仅 1 个成功，另 1 个返回冲突；
  - 中途校验失败触发事务完整回滚，不留下半条关联记录或更新 Head。

## 五、后续 Runtime 接入约定

本节只规定后续接口使用边界，本轮不实现调用编排，也不修改 Agent。

- 开始执行前保存用户输入。
- 执行工具前保存启动记录。
- 每个工具完成后及时保存结果，不等待整批工具结束。
- 任务结果落盘后再通知完成。
- Runtime 负责 Agent 的创建、查找、停止与关闭，协调归档、分支切换及存储失败后的处理。
- 同一会话同时只由一个 Agent 执行；不同 Agent 使用各自会话，通过消息或结果交接协作。同项目文件冲突属于 Runtime／工具执行环境的后续设计。
- 不在持有 Agent 状态锁时执行数据库 I/O；具体执行边界在 Runtime 接入阶段落实。
- 显式恢复前，由 Runtime 确认该 Run 已无运行实例；不因普通读取而中断任务。

### Agent history 的后续切割

不能将当前 Agent 的整个 `history.go` 搬到 Session。按职责拆分：

| 当前内容 | 后续职责与归属 |
|---|---|
| 完整历史、分支关系、消息来源 | Session 保存和读取 |
| `a.history` | 可保留为当前分支的内存缓存，持久化事实以 Session 为准 |
| `messageOrigin` | 来源保存到 Entry.Origin；若请求准备仍按消息指针查询，只保留可重建的临时索引 |
| `run.messages` | 继续表示本次 Run 产生的消息，用于运行结果 |
| `prepareRequestHistory` | 留在 Agent，构造本次模型请求使用的历史 |
| `pairToolResults` | 留在 Agent，整理请求中的工具配对；不改写 Session 原始事实 |
| `projectAssistantThinking` | 留在 Agent，依据当前模型及历史来源决定思考块能否回传 |

Session 必须提供两种读取能力：按 Run 读取一次任务，以及按当前分支读取完整 Entries 与 Origin。前者用于任务查看，后者供 Agent 准备模型上下文。

请求准备中为缺失工具结果生成的说明不写回原始历史；过滤失败响应、跨模型思考处理和未来 Memory 策略都不塞进 Session。本轮只准备这些读写能力，实际切割和 Agent 适配留给后续 Runtime 计划。
