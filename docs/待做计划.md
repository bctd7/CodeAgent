## 一、修复消息流与错误语义

**现有问题**

- `Abort` 和内部错误处理先读取快照，再另行加锁终止，可能遗漏两次加锁之间发布的内容。
- 外部错误被当作 `InternalErr`，用户可读的 `ErrorMessage` 却为空。
- `IsTerminal()` 将空状态也判断为终态。
- 消费过的事件槽位虽然清零，底层队列仍持续增长。

**修改要求**

- 保留 `StreamReader`、`StreamWriter` 和 `Result` 的主体接口。
- 将终止操作集中到持锁的内部方法；取消和内部失败在同一次锁内取得最新快照并完成终止。第一次终止生效，后续调用不覆盖结果。
- 失败和取消时清空 `StopReason`；成功必须有明确的成功结束原因。
- `IsTerminal()` 显式判断已定义终态，空值不算终态。
- 队列读空时重置切片长度和读取索引；暂不引入背压、事件丢弃或复杂环形缓冲。
- 保持 `Result()` 不依赖事件消费；仅调用 `Result()` 的使用方式仍然有效。
- `Next(ctx)` 的取消只停止本次等待；终止请求仍通过父 context 或 `Close()`。

**错误约定**

| 发生位置 | 处理方式 |
|---|---|
| 建流前配置、请求编码或 URL 构造失败 | `Stream` 直接返回 error |
| 建流后网络、HTTP、协议响应失败 | 最终消息为 `StateError`，填写具体 `ErrorMessage`，`InternalErr=nil` |
| 用户取消或超时 | `StateAborted`，保留已生成内容，给出对应提示 |
| 本项目违反事件流契约 | 统一用户提示，具体原因放入 `InternalErr` |

`Complete` 保留现有返回语义，补充 `defer stream.Close()` 和调用说明：调用方既要检查返回 error，也要检查消息状态。

## 二、确定快照所有权，修复内容累积

**现有问题**

OpenAI 适配器发布文本时只保留文本，发布思考时只保留思考；读取失败时又使用初始空消息收尾。最终内容还会被固定重排为“文本、思考”。

**修改要求**

- 每个适配器维护一份完整的累积消息，文本、思考和工具调用共同进入 `Content`。
- 内容块索引稳定，按首次出现顺序分配；不得因另一个块更新而丢掉已有内容。
- 所有内容事件正确填写 `ContentIndex`，补齐对应的 Start、Delta、End 事件。
- 出错使用当前累积消息收尾，不再使用 `initial` 覆盖结果。
- 明确请求在流结束前由调用方保持只读；已发布事件和最终结果也由消费者保持只读。
- 发布快照时只复制 `Content` 切片；字符串直接复用。
- 工具参数原始 JSON 在适配器私有缓冲中累积，完整解析后一次性赋给 `Arguments`，之后不修改该 map。因此不需要递归复制参数。
- 不增加 `CloneRequest`、`CloneModel`、`CloneMessage` 等通用深拷贝体系。

保留 `ContentBlock` 的扁平结构及现有消息接口，不为类型风格进行大规模重写。删除 `Complete` 中废弃注释代码，纠正“Model 是纯值类型”等不准确注释。

## 三、增加 TOML 配置与协议调度

采用已确认的 **Provider 默认值＋模型覆盖协议** 结构。配置只在装配层读取，适配器不访问配置文件或环境变量。

配置示意：

```toml
default_model = "gateway/coder"

[providers.gateway]
base_url = "https://example.com/v1"
api_key = "填写实际凭据"
api = "openai-completions"

[providers.gateway.headers]
X-Client = "CodeAgent"

[providers.gateway.models.coder]
id = "实际模型ID"
max_tokens = 8192

[providers.gateway.models.coder.openai]
reasoning_effort = "high"
max_tokens_field = "max_completion_tokens"

[providers.gateway.models.claude]
id = "实际Claude模型ID"
api = "anthropic"
max_tokens = 8192

[providers.gateway.models.claude.anthropic]
thinking = "adaptive"
effort = "high"
```

以上地址和模型名均为占位符，不提供未经验证的可用模型清单。

**配置和接口**

- 增加独立 `config` 包，使用 `github.com/BurntSushi/toml` 解码。
- 提供 `Load(path)`，以及按 `provider/model_alias` 解析模型的方法。
- Provider 保存 `base_url`、`api_key`、`api`、`headers`；模型保存真实 ID、能力、上下文限制、输出限制、价格及协议选项。
- 模型未写 `api` 时继承 Provider；不按模型名称或 key 推断协议。
- 同一 Provider 的模型共用地址和凭据。不同协议若需要不同地址，配置为两个 Provider；本轮不增加模型级地址和凭据覆盖。
- 解析结果装配为现有 `llm.Model` 和请求选项；凭据不进入消息、事件或模型元数据。
- 增加最小的统一 `Stream(ctx, request)` 调度入口，依据 `Model.API` 选择两种适配器。使用直接分支，不建立动态插件注册系统。
- OpenAI Client 删除 `envKey` 和 `os.Getenv`，从 `Request.Options` 获取凭据和请求头；两个客户端均允许注入 `*http.Client`。
- 普通请求选项继续使用已有 `Temperature`、`MaxTokens`；协议专属参数采用明确的结构体，不用任意 JSON 覆盖请求体。

**默认规则**

- 启动入口接受 `-config`，默认读取当前目录的 `config.toml`；本轮不搜索多个目录、不合并配置、不热更新。
- 配置缺失或格式错误直接报告，不静默回退。
- 校验模型引用、协议名称、URL 和必要数值；不建立全量模型能力验证表。
- API key 允许为空，以支持无鉴权服务；为空时不自动生成鉴权头。
- 先设置协议默认请求头，再应用配置中的 headers，允许网关显式覆盖。
- `base_url` 包含所需版本前缀，适配器仅追加 `/chat/completions` 或 `/messages`。
- 提供占位符示例配置，实际凭据配置不纳入版本管理。

参考依据：OpenCode 在 Provider 下组织连接参数和模型；Codex 在 Provider 配置中组织地址、鉴权和协议；本地 pi-agent-go 支持模型覆盖协议。仅借鉴组织方式，不复制它们的完整配置系统。[OpenCode](https://opencode.ai/docs/providers)、[Codex](https://developers.openai.com/codex/config-reference)

## 四、补齐 OpenAI Chat Completions

**请求侧**

- 接通凭据、headers 和思考选项。
- `reasoning_effort` 只在显式配置时发送。
- `max_tokens_field` 支持 `max_tokens` 与 `max_completion_tokens`，默认沿用当前的 `max_tokens`；一次请求只发送一种。
- 输出限制优先使用请求选项，其次模型配置；均未设置时省略。
- 工具参数序列化失败必须返回错误，不能继续忽略 `json.Marshal` 错误。
- 文本块拼接不擅自加入换行；换行应来自原始文本。
- 保留当前 `reasoning_content` 兼容能力，不扩展大量厂商别名字段。
- 用户图片继续使用 data URL；本轮 Chat Completions 工具结果限定文本，对工具结果图片明确报不支持。

**响应侧**

- 只处理 choice index 0，不把多个候选答案合并。
- 按工具调用 index 累积 ID、名称和 arguments，支持多个工具调用交错到达。
- arguments 在工具块结束时解析为 JSON object；非法参数作为外部响应错误报告，保留已有内容，不修补 JSON、不伪造参数。
- 正确处理仅含 usage 的 chunk，以及缺少 delta 的结束 chunk。
- 接通响应 ID、响应模型、原始结束原因、usage 和费用计算。
- 优先识别流内 provider error，不能最后只显示“未知 finish_reason”。
- 收到 finish reason 后继续读取可能存在的 usage；正常结束必须已有可识别结束原因。连接读取错误仍按失败处理。
- `content_filter` 等失败原因给出明确提示；未知原因保留原始值，不能伪装为正常结束。
- HTTP 错误读取最多 64 KiB 的响应体，优先提取服务端错误消息；不输出请求头、凭据或完整请求体。

**用量口径**

`Input` 表示未缓存输入；`CacheRead` 单独记录。OpenAI 的 prompt tokens 减去 cached tokens 后填入 `Input`。`Reasoning` 是 `Output` 子集，不重复计入 Total 和费用。

## 五、增加 Anthropic Messages 与最小思考配置

复用消息模型和流接口，独立实现请求与响应转换；不将 Anthropic 事件伪装成 OpenAI chunk。

**基础能力**

- 使用 `/messages`，默认鉴权为 `x-api-key`，设置 `anthropic-version: 2023-06-01`。
- 系统提示使用顶层 `system`。
- 用户内容支持文本和 base64 图片；assistant 工具调用映射为 `tool_use`。
- 工具结果映射为 user 消息内的 `tool_result`，保留调用 ID 和错误标记；连续工具结果合并到同一 user 消息，支持文本与图片。
- Anthropic 请求必须有正数 `max_tokens`：从请求或模型配置取得，缺失时报配置错误，不猜模型上限。
- 处理 message、content block、文本、思考、签名、工具 JSON、usage 和 error 事件。
- `message_stop` 才表示完整结束；此前断流报告失败。忽略 ping 和无关新增事件；未知内容块明确报告不支持，避免静默丢失内容。
- `end_turn`、`stop_sequence` 映射普通结束，`max_tokens` 映射长度结束，`tool_use` 映射工具调用；拒绝和本轮不支持的暂停原因给出具体说明。
- usage 中累计输出值采用更新，不重复相加；缓存读取、缓存写入独立计费。

**思考配置**

- OpenAI：可选 `reasoning_effort`。
- Anthropic：可选 `thinking`（`enabled`、`adaptive`、`disabled`）、`budget_tokens`、`effort`。
- 未配置的字段不发送；`Model.Reasoning` 不自动开启任何参数。
- `enabled` 要求正数预算且小于本次 `max_tokens`；`adaptive` 和 `disabled` 不携带预算。
- 不内置“某模型支持哪些档位”的目录；服务端不支持时展示具体错误。
- 保留思考内容、签名及 redacted thinking 的不透明数据。为后者增加明确字段，不混用图片数据字段。
- 同协议工具往返完整回传思考块，不修改签名；本轮不承诺会话中跨协议切换。

两种适配器共用最小 SSE 分帧工具，协议结束条件由适配器判断；不要让公共分帧器硬编码 `[DONE]`。保留单事件大小限制，并将多行拼接的换行计入长度。

Anthropic 的块事件、工具 JSON 增量、累计 usage 和签名处理以官方说明为准。[流式事件](https://platform.claude.com/docs/en/build-with-claude/streaming)、[思考配置](https://platform.claude.com/docs/en/build-with-claude/extended-thinking)

## 六、手动验收与交付顺序

不编写自动化测试。将现有模板入口替换为小型手动调用入口，支持选择配置、模型、提示词，以及工具演示模式。

工具演示仅使用一个无副作用的内置工具，例如整数相加：声明工具 → 收到调用 → 本地计算 → 回传结果 → 获取回答。最多进行三轮模型调用，避免演示程序无限运行；这不扩展为正式 Agent 框架。

按顺序完成并手动检查：

1. **消息流修复**：中途取消后保留已收到内容，只出现一个终态。
2. **配置接通**：选择两个模型，确认 Provider 默认协议与模型覆盖均生效；环境变量不影响凭据。
3. **OpenAI 补齐**：文本、思考、工具往返、usage 能正确展示；错误凭据能显示服务端原因。
4. **Anthropic 补齐**：文本、图片、工具往返可用，思考签名在后续请求中保留。
5. **思考选项**：分别运行未配置与显式配置；不支持的参数显示具体错误，不自行重试或降级。
6. **收尾**：最终消息、事件输出与用量一致；普通失败不进入 `InternalErr`。

每项记录“已手动验证”或“尚未验证”。缺少某协议的可用服务时如实保留未验证项，不用代码阅读代替实际验证结论。
