提示词开始
你需要在现有 Go 项目 CodeAgent 中建设 internal/runtime，使已有 Agent 与 Session 协作，形成 CLI、TUI 等应用层可以统一调用的会话运行层。
这是实现任务，不是重新设计整个项目。先阅读当前代码，再按以下边界实施。不要根据个人喜好重构现有包，也不要只提交空接口、占位实现或设计文档。

  二、职责边界，不得混淆
1. Agent 保留执行主体
   保留已有 Submit 队列、Steer、RunHandle、取消、关闭、模型切换时机、模型与工具循环、工具串并行调度、内存上下文和请求历史整理。
   不要把 queue.go、executeRun、工具调度主体搬进 Runtime。
   不要在 Runtime 建第二套任务队列、currentRun 或模型循环。
   不要改变现有普通工具错误、取消、截断及排队任务的处理语义；持久化故障的必要收尾接入除外。
   Agent 不依赖 internal/runtime，也不直接依赖 Session、Store 或 SQL。
2. Session 保留数据业务主体
   负责会话、Run、Entry、工具执行记录、模型来源及当前历史的合法读写和事务一致性。
   Session 不持有 Agent，不执行工具，不启动后台循环，不负责取消任务。
3. Runtime 负责单会话协调
   一个 Runtime 绑定一个 Session 和一个 Agent，负责：
- 会话初始化与上下文恢复
- 模型、工具和执行依赖装配
- 将 Agent 的执行节点接到 Session 的持久化操作
- 当前模型选择的保存与恢复
- 实例故障状态、准入和关闭协调
4. Manager 负责多会话管理
   按 SessionID 管理 Runtime 的创建、复用和关闭，管理会话所有权，提供会话列表及管理操作，协调程序整体退出。
   一个数据库保存多个会话，不是每个会话一个数据库。
   不同进程可以使用同一个本地数据库的不同会话。
5. 应用层只调用 runtime 包
   CLI/TUI 负责解析输入、调用能力和展示结果。
   /usage、/add-dir 等只是命令入口，不在命令处理函数里另建业务规则。本任务不实现这些命令，不扩展多目录能力。
   不向应用层暴露可以直接修改的 Agent、Session、Store 或数据库句柄。可以返回现有任务句柄、只读查询结果和事件。
   三、Runtime 文件与层级
   采用少量按职责命名的文件，建议以下布局作为本次实现基线：
- internal/runtime/manager.go：Manager、初始化、实例登记、会话管理入口、整体关闭
- internal/runtime/runtime.go：单会话 Runtime、用户操作、状态、关闭协调
- internal/runtime/persistence.go：Agent 记录接口的具体实现、类型转换与记录关联
- internal/runtime/ownership.go：会话所有权、进程内协调、跨进程锁生命周期
- internal/runtime/tools.go：现有工具的装配和工作目录适配
- internal/runtime/config/types.go：Runtime 配置、输入参数、快照和必要错误定义
  跨平台锁确实需要时，增加 ownership_windows.go、ownership_unix.go 等平台文件；如果使用经过核实的成熟跨平台锁库，就不要再重复实现平台层。
  测试使用相应的 _test.go 文件。
  不要为了形式完整创建 runtime/store、runtime/sql、runtime/service、runtime/repository。Runtime 没有自己的第二套数据库业务层。
  不要创建大量只有一个转发函数的文件，不要使用 helpers.go、utils.go 收纳无关职责。
  结构体和方法按职责放置，不要求所有接收者方法必须挤在定义结构体的文件里。

  所有新的存储或生命周期等待操作接收 context。已有 Agent 的签名不要为了统一形式而大范围改动。
  五、会话所有权
1. 锁的粒度
   按“数据库身份＋SessionID”取得跨进程独占所有权。只面向同一台机器、本地磁盘，不建设跨机器租约或分布式锁。
   使用真正的操作系统锁或具备对应语义的成熟实现。不能把文件存在、PID 记录或内存 map 当成跨进程锁。
   数据库路径需要规范化，避免相对路径、常见路径别名导致同一个库使用不同的锁身份。不要通过随意删除、重建锁文件来抢占所有权。
   同时处理进程内并发，不能只依赖不同平台文件锁对同一进程重复打开的行为。相同数据库和会话在同一进程中也必须只有一个拥有者。
2. 全局浏览不持有会话锁
   ListSessions 可以返回 ID、标题、更新时间、归档状态等摘要。
   列出一百个会话，不创建一百个 Runtime，也不取得一百把会话锁。
   完整历史、Run 详情等会话内容，通过已取得所有权的 Runtime 读取。
3. 打开会话长期持锁
   先取得所有权，再加载会话内容、执行恢复和创建 Agent。
   空闲时不释放；Runtime 完整关闭后才释放。
   本 Manager 重复打开同一会话，复用同一个可用 Runtime；并发打开只初始化一次。
   其他进程占用时返回可判断的错误，不自动抢占、不结束对方进程。
   正在初始化、关闭或故障收尾的实例不能被当作不存在，再创建一个替代实例。
4. 列表管理操作短暂持锁
   未打开的会话执行重命名、归档或取消归档时，临时取得所有权，操作完成后释放，不加载历史、不创建 Agent。
   已有本 Manager 的 Runtime 时，通过已有拥有者协调，不能再套一把互相等待的锁。
   其他进程占用时拒绝修改。
   归档继续沿用已有规则：存在活动 Run 就拒绝，不自动取消再归档。归档成功后关闭对应空闲实例。
5. 锁释放条件
   Close 等待超时，不等于执行已停止。只要仍有 Agent、工具或落盘收尾可能运行，就保留所有权和关闭中的实例登记。
   会话所有权锁可以跨数据库读写一直持有。禁止的是持有 Agent 状态互斥锁或 Manager 全局登记锁时进行数据库 I/O、调用外部回调或阻塞等待。这两类锁不要混为一谈。
   六、打开与恢复
   OpenSession 的完整流程：
1. 通过进程内协调及跨进程锁取得初始化权
2. 检查会话存在且未归档
3. 已绑定工作目录则调用现有验证能力；目录失效就打开失败，不创建目录、不降级运行
4. 检查当前会话的遗留未结束 Run
5. 确认已持有独占所有权后，通过既有恢复接口将遗留 Run 标记为 aborted，说明为程序中断
6. 读取 GetCurrentHistory 返回的当前分支 Entries 和 Origin
7. 解析会话当前模型，装配工具、Agent 和记录接口
8. 全部成功后才登记为可用并返回
   未绑定工作目录允许纯聊天。
   恢复只处理当前会话，不能因为一个进程启动而把整个数据库的未结束 Run 全部中断。
   恢复默认静默，不强制向用户弹提示。
   不自动续跑旧 Run，不恢复旧排队任务，不重放工具。
   有工具启动记录而无结果，只能表达结果未知，不能认定未执行。
   已发生的文件修改不自动回滚。
   失败时释放本次创建的资源和所有权，不留下半初始化 Agent。已经合法提交的旧 Run 中断记录不用改回运行中。
   Session 的 Init、GetSession、OpenSession 本身仍不自动恢复；恢复编排只在 Runtime。
   七、Agent 与 Session 的最小接入
   需要在 Agent 声明少量同步、可返回 error 的记录接口，由 Runtime 实现。
   它是执行所需的内部协作接口，不是可任意排序、可随意跳过的插件 hooks，也不是另一个事件总线。
   建议使用 Recorder 作为接口名称，覆盖以下既有业务动作：
- StartRun
- RecordStep
- AppendMessage
- RecordToolStart
- AppendToolResult
- FinishRun
  方法参数只能使用 Agent 自己的类型、llm 类型和必要的基础标识，不能引入 Session 类型。
  AppendMessage 保存 assistant 后，可以返回不透明的消息关联标识。Agent 只将它带给随后的工具记录调用；Runtime 内部把它对应到 AssistantEntryID。不要让 Agent 查询数据库，也不要只靠 ToolCallID 全局关联。
  接口可通过 agent.Config 注入，兼容未接入持久化的现有 Agent 使用场景和 demo。不要强迫所有 Agent 使用数据库。
  允许的其他最小 Agent 改动：
- 注入跨重启唯一 RunID 的生成能力；Runtime 必须使用 UUID 等唯一标识
- 初始历史恢复时同时传入模型来源信息
- 必要的执行边界预约、收尾和故障原因处理
  现有 modelOrigin 可做必要的导出或窄类型调整，不建立庞大的统一类型框架。
  恢复来源必须对应 Agent 实际持有的 assistant 消息对象；如果复制了消息，需要正确重建索引，不能让指针索引失效。
  禁止直接把数据库调用塞进持有 a.mu 的 prepareRequest、finishRunAndUnlock 或 changeModel。
  采用最小的边界协调：锁内确定本轮操作和状态，锁外完成保存，再在受控边界继续。收尾期间不能继续接受随后被丢弃的 Steer，也不能提前取下一任务。
  Recorder 内不能同步调用等待当前执行结束的 Agent.Close，否则会等待自己。
  八、正常执行与持久化顺序
1. Submit
   输入进入 Agent 原有队列，立即返回句柄。
   排队本身不创建数据库 Run，不追加会话历史。
   排队期间取消或程序退出，不恢复这条输入。
2. 真正出队开始
   先调用 Session.StartRun，原子保存 Run、用户消息和相关位置，成功后才开始模型调用。
   保存失败不得把该任务继续当成已开始执行的正常 Run。
   空标题的自动补全在用户消息真实保存后执行，复用 SetTitleIfEmpty，不覆盖用户标题，不通过大模型生成标题。该辅助操作失败不使整个任务失败。
3. Steer
   沿用原有接收与消费规则。只有实际消费进入当前 Run 的纠正，才保存为普通 UserMessage。
   未消费且被取消的纠正，不凭空写入历史。
4. 模型请求
   每次实际调用前记录一次 RecordStep。请求准备失败不虚增调用次数。
   最终 assistant 消息与实际请求的 Origin 一起保存，成功后才进入工具执行或正常终态处理。
   失败、取消、截断响应按既有记录规则保留，不能拿请求投影后的消息替代原始记录。
   流式增量可以实时展示，不要求逐字符写库。
5. 工具执行
   先保存对应 assistant，取得关联标识。
   真实调用工具 Execute 前，RecordToolStart 必须成功。
   未知工具、因取消或纠正而跳过的调用，不伪造启动记录；按既有语义产生明确结果并保存。
   每个工具完成后及时 AppendToolResult，不等整个并行批次结束。
   Session 按实际提交顺序记录；Agent 仍可以按模型原始调用顺序组织下一次请求。不能为统一两者顺序而破坏任意一边。
   ToolCallID 不是全局唯一，关联始终包含对应 assistant。
6. Run 结束
   先确定最终状态并完成 Session.FinishRun，再完成句柄、发布最终结束信息、允许下一项任务开始。
   不能先把 currentRun 清空、对外显示空闲，再慢慢保存上一轮结果。
   排队任务未实际开始时，不调用 FinishRun 去更新一个不存在的数据库 Run。
   九、持久化失败
   关键记录保存失败：停止新增模型请求和工具启动，取消在途执行并等待退出，使用有界收尾流程尽力保存已产生的结果。
- StartRun 失败：不调用模型和工具
- assistant 或工具启动记录失败：不继续启动后续工具
- 工具结果失败：不回滚文件，不重新执行工具来补记录
- FinishRun 失败：不宣称正常完成，也不启动下一排队任务
  句柄必须最终能返回包含存储失败原因的结果，不能因为写库失败就永远等待。沿用现有 Wait 的签名与结果约定，明确区分等待 context 超时和任务本身失败。
  Runtime 进入故障状态后拒绝新任务，排队任务明确结束为未执行，不静默丢弃。解决存储问题、关闭后重新打开，再从数据库恢复。
  保存工具完成结果及终态时，使用独立、有超时的收尾 context，不能机械复用已取消的 run.ctx。
  普通用户取消不是持久化故障；真正的存储失败需要保留其原因，不能因为为停止工具而调用 cancel，就被现有取消分支覆盖成普通 aborted。
  不要无限重试。提交结果不确定时，不盲目重复追加消息，先核对真实记录；不能用重试有副作用的工具代替记录恢复。
  正常工具业务错误，例如文件不存在或参数错误，仍按 Agent 原有逻辑返回给模型处理，不一律使 Runtime 故障。
  十、取消与关闭沿用已定语义
  不要重新设计 Agent 的 Cancel、Steer、队列与 Close。
  取消一个正在运行的任务，完成必要保存后，会话继续保持打开和所有权；其他排队任务按现有 Agent 规则处理。
  关闭 Runtime：停止准入，结束排队任务，取消活动任务，等待 Agent 和落盘收尾，释放专属资源，最后释放所有权。
  关闭不删除、不自动归档会话。
  Manager.Close 先阻止新会话打开，协调全部 Runtime 关闭，最后关闭共享数据库。一个实例关闭失败，不应阻止尝试关闭其他实例；但不能提前关闭仍被收尾使用的存储。
  重复关闭复用同一次关闭过程。等待调用的 context 超时，不得取消必要收尾或伪造已关闭状态。
  十一、模型选择持久化
  本项目没有默认模型回退规则，只有会话当前选择的模型。
  在 session/config 中增加小型 ModelSelection，保存模型配置引用，必要时保存明确的非敏感请求参数；由 SessionInfo 持有。
  模型引用使用现有 internal/config.ModelEntry.Ref 的含义，不能只保存可能重名的 Model.ID。
  如果支持请求参数覆盖，使用只包含 Temperature、MaxTokens、OpenAI、Anthropic 等允许字段的小结构。不能整体序列化 llm.RequestOptions，因为其中包含 APIKey 和 Headers。
  凭证、鉴权头从现有配置包解析，不能写入会话数据库、快照或日志。
  Session 内只增加这一能力所需的类型、业务方法、Store 读写及 SQL/迁移：
- 更新当前模型选择，可使用 SetModelSelection 这个明确名称
- 创建会话与初始模型选择应在同一事务保存
- 如需保留既有 CreateSession 签名，可增加 CreateSessionWithModel 并复用内部实现，不破坏旧调用方
  沿用已有 user_version 和迁移机制。旧会话没有模型选择时保持缺失，打开时要求调用方明确补充；不能按配置列表第一项或最后一条消息 Origin 猜测。
  Runtime.SetModel 的职责仅是在既有 Agent.SetModel 外协调校验和持久化，不另造模型切换系统。
  持久化字段表示最后成功接受的模型选择。某次 A 请求仍在进行时选择 B，A 的 Origin 仍是 A，后续请求与重新打开使用 B。
  串行协调同一会话的模型选择更新，避免数据库最后保存 B、Agent 最后收到 C。必要时短暂协调请求准备边界，但不能在 Agent 状态锁内执行数据库 I/O。
  保存失败时不接受新选择；已经保存而 Agent 更新失败时进入故障状态，重新打开按持久化选择恢复，不能带着不一致状态继续。
  模型引用失效或配置不合法时明确返回错误，保留原选择，不自动替换。OpenSession 可接受显式替换选择，经校验和保存后初始化。
  十二、工具在 Runtime 初始化时完整装配
  初始化就注册当前平台的全部既有基础工具，复用原有名称、描述、Schema、ParallelSafe 和执行算法。
  不能等绑定目录后才新增工具，也不为了 Runtime 改写 read/edit/grep/find/ls/write/shell 的主体实现。
  注意现有 basic.New 在 WorkingDir 为空时会回退到进程当前目录。Runtime 的未绑定会话不得走这个回退路径后直接执行文件工具。
  允许在 runtime/tools.go 做小型执行适配：
- 启动时提供完整稳定的工具定义
- Execute 时取得该会话绑定的目录，再调用既有工具实现
- 未绑定目录时返回清楚的工具业务错误，不自动使用 os.Getwd
- 首次绑定成功后，相同工具入口使用新目录，不重建 Agent 或改变工具集合
  可以复用现有 NewReadTool 等构造函数，避免复制 Schema。若确实需要改 tools 包，只允许最小的目录注入支持，不能更换整体框架。
  不要调用 os.Chdir，也不要新增每次执行前重新检查目录存在性的统一流程。目录有效性在首次绑定和每次重新初始化时检查，运行中的普通文件系统错误由工具原有执行处理。
  工作目录允许为空，首次绑定后不可更换或清空。绑定仍遵守已有活动 Run 限制，并与任务开始边界协调，不能只看数据库暂时还没出现 Run 就判定可以并发绑定。
  不要自行引入尚未确认的“队列非空就拒绝所有管理操作”规则，也不要静默取消、转移已排队输入。
  十三、事件和快照
  复用 Agent.OnEvent 和 Snapshot，通过 Runtime 向应用层提供。
  多会话输出需要能识别 SessionID，可在 Manager 配置的回调参数中补充，不必修改全部 Agent 事件类型。
  Runtime 快照补充实例初始化、可用、故障、关闭中的状态；任务执行状态仍来自 Agent，不复制维护第二套 running/currentRun 状态机。
  本次不建立消息总线、持久化事件日志、网络订阅协议或事件重放系统。
  对外事件用于观察，不能依赖 UI 回调来保存数据。
  不持有 Agent 状态锁调用用户回调；回调异常不能导致重复执行工具或破坏持久化顺序。沿用并注明现有回调不要同步等待当前 Run 或 Close 的约定。
  十四、初始化和版本更新
  共享数据库由 Manager 初始化阶段打开，复用 Store.Open、Init、Close。Runtime 正常会话业务不绕过 Session 直接调用 Store 或 SQL。
  需要升级时先完成升级，成功后才允许任务运行。未知版本、升级失败或数据库被占用，返回明确错误。
  按个人用户使用方式要求升级时关闭其他实例，不建设在线跨版本升级、分布式迁移锁或后台服务。
  事务回滚、已有数据保护和旧版兼容检查仍需保留，不能把用户不会恶意操作理解成可以忽略数据库错误。
  十五、明确不做的事项
- 不实现 SubAgent、会话派生、父子消息转交
- 不新增用户可见的历史回退、分支切换命令或文件回滚
- 既有 Session.SwitchBranch 保留，不删除、不为了本任务改写
- 不建设通用 hooks/插件框架
- 不实现 CLI/TUI/Desktop 界面和命令系统
- 不新增多工作目录或目录沙箱
- 不更换 SQLite、Provider 或 LLM 协议实现
- 不修复与本任务无关的工具问题
- 不把共享数据库改成每会话一个数据库
- 不未经要求提交、推送或合并到 main
  十六、必须实际验证
  测试使用临时数据库、可控的假 StreamFunc 和假工具，不调用付费模型，不依赖真实 API Key。
  至少覆盖：
1. 同会话并发打开只创建一个 Runtime；不同会话可并行
2. 两个真实子进程争用同一会话时只有一个成功；不同会话均能打开
3. 空闲实例仍持锁；关闭后可接管；进程退出后可接管
4. 列表不取得所有权；列表修改使用短锁；其他拥有者存在时拒绝修改
5. 初始化失败无实例、goroutine 和锁泄漏
6. 遗留 Run 只在取得对应会话所有权后静默中断，不重放工具
7. 历史和 Origin 正确恢复，同源思考处理不因恢复丢失来源
8. Submit 排队不落库，真实开始才有 Run；排队取消不生成伪 Run
9. StartRun 保存失败时模型完全未调用
10. assistant 保存失败不执行工具；工具启动记录失败不调用 Execute
11. 两个并行工具中，快工具完成后可先查到其结果，不必等待慢工具
12. 相同 ToolCallID 出现在不同 assistant 时不会串配
13. 未知、跳过的工具有结果但无伪造启动记录
14. 正常 FinishRun 提交后，句柄才完成；存储失败仍明确结束句柄，不启动下一个任务
15. 用户取消后仍可保存已有结果与 aborted；存储故障不被取消状态掩盖
16. Close 等待超时不释放仍在执行的会话锁；重复关闭行为一致
17. 模型选择可持久恢复；无默认回退；旧请求 Origin 不被新选择污染；数据库中无凭证
18. 所有工具启动时可见；未绑定时不使用进程 cwd；首次绑定后同一入口使用绑定目录
19. 模型和目录更新与执行边界不发生竞态；不持 Agent 状态锁执行数据库操作
20. 原有 Agent、Session、工具使用方式没有被无关重构破坏
    保留有价值的回归测试，不以删除测试文件作为完成步骤。
    执行 gofmt、相关包测试、go test ./...、go build ./...、go vet ./...。环境支持时执行竞态测试；跨进程锁必须有实际子进程测试，不能只用 goroutine 测试冒充。
    Windows 是重要目标平台。没有实际运行过的平台明确列为未验证，不能把交叉编译成功写成该平台锁行为验证通过。
